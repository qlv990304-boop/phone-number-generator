Randomized parser testing

Random phone number generator for testing: replay a failure

Use random phone-shaped inputs to explore parser edge cases, keep SMS delivery disabled, and save the test seed and counterexample path with the region and numbering-metadata version. A format-shaped result does not show that a number is assigned or can receive a message.

Developer guides · Updated September 27, 2026

What a random phone number can prove

A random phone number generator can give a parser a wider set of inputs than a short hand-written list. It can help find edge cases in country context, separators, lengths and normalization. It cannot prove that a value belongs to a subscriber, is currently reachable or can receive SMS.

Keep those claims separate: parsing is a software behavior; allocation and reachability are network facts. Google's libphonenumber FAQ explains that numbering metadata cannot tell whether a number is currently assigned to a specific user or reachable. Treat generated values as test inputs, not contact targets.

Capture enough context to replay the failure

A seed alone may not describe the complete test that failed. Store the generator and property-test library versions, the failing path, the default region, the phone-number metadata version, the property name and the runner configuration. Keep these values together in the CI artifact so another developer can reproduce the same case.

In fast-check, the documented seed and path parameters can replay a failing property. The path is used with the seed. Preserve the versions and region around that pair because they are part of your own parser's test setup.

Test useful boundaries, not arbitrary digit noise

Generate structured input variations that map to a rule your product actually supports. Keep the expected behavior beside each property; don't assume every plausible-looking string should pass.

For every generated input, assert one meaningful invariant. For example, if the parser accepts an input and returns a canonical international value, parsing that canonical value again under the same region and metadata should return the same canonical value. If your product has different rules, encode those rules explicitly instead of turning a convenient assumption into an oracle.

Replay a failing property

The exact integration depends on your test runner, but the replay parameters should come from the failing run rather than a newly chosen seed:

import fc from 'fast-check';

const replay = {
  seed: Number(process.env.FC_SEED),
  path: process.env.FC_PATH
};

fc.assert(phoneParserProperty, replay);

Replace phoneParserProperty with your property and pass the seed and path reported by the failed run. Pin the phone-number metadata package and default region too. A replay that silently uses newer metadata may exercise a different rule.

  1. Save the seed, path, versions, region, property ID and command in the restricted CI failure artifact.
  2. Run that single property with the saved values and confirm it reproduces before changing code.
  3. Keep the minimized counterexample as a named regression case after fixing the defect.
  4. Review the regression case when updating parser or numbering metadata versions.

Keep test generation away from live delivery

Randomized parsing belongs in a local or isolated test environment. Disable outbound SMS and voice at the application boundary, not only in the test data factory. If a separate delivery check is necessary, use a provider sandbox or an allowlisted line the team controls and is authorized to test.

A public developer discussion has described an integration script sending unintended messages to real phones. That is an anecdotal report, not a measure of how often it happens, but it illustrates why input generation and message delivery should be independently controlled. Never send a generated number a text just to see whether it works.

In general logs, record the property ID and run ID instead of a complete phone value. Keep raw or minimized inputs in a restricted test artifact only when a reviewer needs them; do not forward them to analytics, screenshots or public issue reports.

Frequently asked questions

How do I repeat a failing random phone-number test?

Save the property-test seed and counterexample path, then rerun with the same parser version, phone metadata, region and test command. In fast-check, replay uses the seed together with the path.

Can a random phone number generator create a number that reaches a real person?

It can produce a string that resembles a real number. Format alone does not establish assignment, and a random value must never be contacted as a test. Keep outbound delivery disabled or use an authorized provider sandbox.

Should parser tests send SMS?

No. Parser tests should stay offline. Use a separate, explicitly authorized delivery test with a sandbox or controlled destination when message delivery is the behavior under test.
