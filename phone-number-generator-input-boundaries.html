Phone Number Generator: Test Extraction and Whole-Field Input Separately

Answer: test text extraction and whole-field parsing separately. Then enforce your field's own input contract: a parser can recognize formatted digits or an extension even when your API permits only one canonical number.

Developer guides · Published October 14, 2026

Define the field before choosing a parser

The library's official API documentation describes extraction from surrounding text and the extract: false option for whole-input parsing. Our experiment pins that library and records the two modes independently. Neither mode is an allocation or delivery check.

A prose-import feature may intentionally find a candidate inside a sentence. A phone form may allow local punctuation and a separate extension. Our sample machine API has a narrower contract: one ASCII plus-prefixed digit string, with optional outer ASCII spaces removed before parsing. These are different entry points with different accepted languages. Choose the contract deliberately instead of treating any successful parser result as permission to save the raw input.

Our 16-input comparison

On October 14, 2026, we ran Node v24.19.0 with libphonenumber-js/max 1.13.15. The fixed US fixture was +12025550123. Each of 16 inputs was parsed once with extraction enabled and once with it disabled: 16 × 2 = 32 parser invocations. Parser outputs below are observations, not universal expectations. All 16 separately authored API-policy assertions passed: exactly the canonical string and the string with outer ASCII spaces met our sample syntax policy.

A field validator that checks only the extracted object's isValid() would accept these surrounding-text cases in this pinned experiment. We therefore record the original input, parsing mode, canonical output and policy outcome as separate columns in the test record.

The repeated-plus, middle-plus, two-values and empty inputs returned NOT_A_NUMBER in both modes. This is evidence for these specific strings and this package version. It does not reproduce every outcome from another library, language or historic version.

Whole-input parsing still has a phone grammar

Our whole-input mode accepted the national display, spaced international display, nonbreaking-space display, fullwidth digits and extension syntax. The fullwidth input normalized to the same ASCII canonical number; the extension stayed in a distinct property as the string 0042. If an API contract forbids either representation, successful whole-input parsing alone will not enforce that policy.

The tel URI parsed with extraction enabled but failed with extraction disabled. Outer spaces, tabs and a trailing newline also failed in whole-input mode on the raw strings tested here. We did not pre-trim those parser observations. In the API path below we explicitly remove outer ASCII spaces first; that explains why its outer-space case is accepted without contradicting the raw parser result.

Decide whether to normalize Unicode digits or whitespace at a named boundary and test that operation separately. A broad replace operation that deletes every non-digit character could erase evidence of two numbers, an extension or misplaced plus sign. This experiment does not recommend rejecting Unicode in every human-facing form; its narrow API policy is a worked example.

Make syntax, parsing and fixture identity separate checks

function apiField(input) {
  if (typeof input !== 'string') return false;
  const text = input.replace(/^ +| +$/g, '');
  const match = /^\+[1-9][0-9]{7,14}$/.exec(text);
  return !!match && match[0] === text;
}

assert.equal(apiField(raw), expectedSyntaxDecision);
if (apiField(raw)) {
  const text = raw.replace(/^ +| +$/g, '');
  const parsed = parsePhoneNumberWithError(text, { extract: false });
  assert.equal(parsed.ext, undefined);
  assert.equal(parsed.number, fixture.e164);
}

The eight-to-fifteen digit limit is the sample API's broad shape constraint, not a universal minimum length or a test of assigned calling codes. It rejects formatting and extension characters before the parser sees them. The canonical-equality assertion belongs to these known fixture cases; arbitrary customer inputs have no preselected fixture identity to compare with.

We also measured a JavaScript anchor control using the canonical value followed by a newline. The anchored expression without the multiline flag returned false; the same expression with m returned true because it could match the first line. Do not enable multiline mode for a single API field. We additionally compare match[0] with the complete transformed text so the accepted extent is visible in the contract.

For our two accepted inputs, the complete API path trims only outer ASCII spaces, parses the remaining international value with extraction disabled, requires no extension and checks the exact fixture identity. Preserve independent country-plan or validity diagnostics if your product needs them; the syntax helper is not a complete production validation function.

Sources, limitations and related tests

The base example falls within NANPA's documented fictional 555-0100 through 555-0199 interval. Both numeric values in the two-values control use that interval. The fixture retains fictionalOnly: true and deliveryAllowed: false. Added punctuation, digits in another script and the made-up extension are test representations, not live dialing instructions. No call, message or account verification was attempted.

Google's FAQ distinguishes parsing from checks on assignment or reachability. Its behavior is not assumed identical to this JavaScript rewrite. The ECMAScript specification defines regular-expression assertions; our local control supplies the measured JavaScript result.

For the general architecture see validation layers and regex limits. For formatting a complete accepted fixture and returning to its canonical identity, see display round trips. The current matrix targets raw-input acceptance before that display workflow.

Questions from a real validation problem

A public English developer question asks about libraries and regexes accepting repeated plus signs and how to choose a validation matrix. We use that single question as a problem signal. We do not infer its author's location, prevalence, current library behavior or numbering rules from it.

Does a successful parse prove the whole input was a phone number?

No. In our extraction-enabled runs, both the labelled prefix and trailing prose produced the fixture. Whole-input mode rejected those exact strings.

Does extract: false enforce an E.164-only API field?

No. Our whole-input mode also accepted national formatting, nonbreaking spaces, fullwidth digits and an extension. Apply a separately documented input policy.

Should I remove every non-digit character before validation?

Avoid erasing evidence before checking the field contract. Keep the original input and perform only the transformations your entry point explicitly permits.

Are repeated plus signs always accepted by phone libraries?

No such conclusion follows. Both modes rejected our repeated-plus case. Results from an older report or a different implementation need their own reproducer.

Can these generated test representations receive a code?

They are fictional offline fixtures with delivery disabled. Parsing and syntax acceptance do not establish a working line or permission to send.
